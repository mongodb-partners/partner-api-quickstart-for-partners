MongoDB Atlas · Partner Guidance

M0 is for learning. Your customers are building real products.

If your product provisions MongoDB Atlas for customers, every workload that serves real users or real business data belongs on a paid tier (M10+ dedicated, or Flex for lightweight dev/test). This guide shows what M0 blocks, why paid tiers belong in dev and stage too, and exactly how to get each customer there.

512 MB storage cap on M0 500 max connections on M0 0 backups · uptime SLA on M0 M10+ unlocks the full platform

M0 vs paid clusters — the real difference

M0 is a sandbox: shared resources, hard caps, and no safety net. Paid tiers are the same database engine with the controls real applications need.

Capability 🆓M0 — Free 〰️Flex ⚡M10+ — Dedicated
Storage 512 MB 5 GB 10 GB and up, with storage auto-scaling
Compute Shared RAM & vCPU Shared, burstable Dedicated RAM & vCPUs — predictable performance
Max connections 500 500 1,500+, scaling with tier
Auto-scaling ✗ None ✗ Manual only ✓ Compute and storage auto-scaling
Backups ✗ No backups ✓ Daily backups ✓ Customizable backups & restore options
Uptime SLA ✗ None ✗ None ✓ Production uptime SLA
Performance tooling Basic monitoring only Basic monitoring only ✓ Performance Advisor, profiler, real-time metrics
Private networking ✗ ✗ ✓ VPC peering / private endpoints
Auditing & customer-managed keys ✗ ✗ ✓ On eligible dedicated tiers
Search indexes 3 10 Unlimited — room for AI/vector workloads

Specs as shown in the Atlas tier picker (see the upgrade screenshot below). Dedicated tiers scale well beyond M10 — storage, RAM, vCPUs, and connection limits all grow with tier size.

Why paid tiers — even for dev and stage

An M0 dev environment hides problems until production. Paid tiers in every environment let your customers use the full potential of MongoDB from day one — and promote to production without a migration.

🚦

Representative load testing

Dedicated RAM/vCPUs and 1,500+ connections mean performance numbers that actually mean something. M0's shared compute and 500-connection ceiling throttle any serious test — so "fast enough on M0" proves nothing.

🛟

Backups in every environment

Practice restores in dev and stage before production depends on them. M0 has no backups at all — one bad migration or accidental delete and the data is gone.

📊

Full observability while building

Performance Advisor, the query profiler, and granular real-time metrics let your customers tune indexes and queries as they build — not as an emergency after launch.

🔐

Security parity with production

Private networking, auditing, and customer-managed keys can only be exercised on paid tiers. If stage can't mirror prod's security posture, the go-live review is where surprises surface.

🧠

AI-ready capacity

M0 allows just 3 search indexes — AI features built on Atlas Search and Vector Search quickly outgrow that. Paid tiers offer unlimited indexes and the memory headroom embedding and retrieval workloads need.

🪜

A clean promotion path

Dev → stage → prod on the same tier family means resizing in place, not migrating off M0 in the middle of a launch. The cluster your customer tests is the cluster they ship.

💡 Rule of thumb for your customers
M0 for a weekend prototype or a first look at MongoDB. The moment a partner demo, a customer, or an employee depends on the application — in any environment — it belongs on a paid tier.

Getting your customer to a paid tier

Two situations, three routes each — pick whichever fits the experience: inside your product with the Partner API, through an AI client with Remote MCP, or directly in the Atlas UI.

💳
Billing, said plainly: paid clusters are billed to the customer's own Atlas organization from the moment a cluster is created or an upgrade is applied. Whatever the route, confirm the tier, region, and expected charges with the customer first — they approve the spend, and the spend is theirs.
A

The customer already has an M0 cluster

Upgrade it in place to M10 — data carries over, no migration needed. Expand a route to see its requirements and steps.

⚠️ Before any upgrade
Plan for roughly ~10 minutes of downtime while the tier scales, preserve any existing snapshots the customer needs beforehand, and restart application clients afterwards to validate connectivity.

🖥️ Route 1 · Atlas UI — fastest; the customer upgrades their own cluster

›

Requirements

Customer's own Atlas login Project Owner or Cluster Manager role
Open the cluster in the Atlas project and choose Edit Configuration / Upgrade.
Select M10 (recommended) — or Flex for lightweight dev/test.
Review the configuration, then Apply changes. Atlas performs a tenant upgrade (~10 minutes of downtime).
Restart application clients and validate connectivity.
💳 Billing
Paid billing to the customer's Atlas organization starts when Apply changes is clicked — the picker shows the tier's hourly price before they confirm.
Atlas UI → Upgrade Cluster: M10 is the recommended target — click to open full size

🤝 Route 2 · Partner API — trigger the upgrade inside your product

›

Requirements

Approved partner onboarding + registered OAuth client User with Project Cluster Manager Org allows third-party app connections
Complete the Partner API OAuth flow (OAuth 2.1 Authorization Code + PKCE) so the customer authorizes your app to act with their Atlas permissions.
With the customer's explicit confirmation, send POST /api/atlas/v2/groups/{groupId}/clusters/tenantUpgrade with the delegated bearer token — using Accept: application/vnd.atlas.2023-01-01+json and the M10 target configuration from the tenant-upgrade schema.
Track the upgrade via the cluster status until stateName is IDLE, then restart app clients and validate.
💳 Billing
The upgrade starts paid billing immediately — surface the tier, region, and expected charges in your UI and get explicit customer confirmation before calling tenantUpgrade.

🤖 Route 3 · Remote MCP — from an AI client or operator workflow

›

Requirements

MCP deployment with atlas-upgrade-cluster available Atlas credentials authorized for the project Customer approval
Configure the AI client with MongoDB MCP and Atlas credentials authorized for the target project.
After confirming the project and the customer's approval, call atlas-upgrade-cluster with target tier M10 — the tool supports Free-to-M10 upgrades.
Poll with atlas-inspect-cluster until the status is IDLE, then restart app clients and verify.
💳 Billing
Paid billing starts when the upgrade is applied — confirm tier and charges with the customer first. Confirm atlas-upgrade-cluster exists in your MCP deployment before relying on it (see the MCP Server tool reference).
B

The customer is starting fresh — no cluster yet

Create the paid cluster directly, so they never hit M0's ceiling.

🤝 Partner API — embedded "Create cluster" flow

The customer authorizes your product to provision Atlas on their behalf.

Requirements

Approved partner onboarding + registered OAuth client Role that permits cluster creation Org allows third-party app connections
Authorize: redirect the customer to https://cloud.mongodb.com/oauth/authorize using OAuth 2.1 Authorization Code + PKCE (response_type=code, client_id, registered redirect_uri, code_challenge, code_challenge_method=S256, state).
Get a token: exchange the callback code at POST https://authorize.mongodb.com/tokens (grant_type=authorization_code, code, code_verifier, redirect_uri, client_id; plus client_secret for confidential clients). Use the returned access token as Authorization: Bearer ….
Select the project: call GET /api/atlas/v2/orgs, then GET /api/atlas/v2/orgs/{orgId}/groups. The customer needs a role that permits cluster creation, and the organization must allow third-party app connections.
Create the paid cluster: after the customer confirms tier, region, configuration, and charges, call POST /api/atlas/v2/groups/{groupId}/clusters with the cluster name, type, and replication specification for the selected paid tier. Poll GET …/clusters/{clusterName} until stateName is IDLE.
Connect securely: create a least-privilege DB user via POST …/databaseUsers, restrict network access via POST …/accessList, then read the connection string from the cluster resource and pass it to the app over a secure channel.
💳 Billing
Charges accrue to the customer's Atlas organization from the moment the cluster is created — always confirm tier, region, and expected charges in your UI before calling the create API.

🤖 Remote MCP — natural-language provisioning

An authorized AI client or operator provisions through MCP tools.

Requirements

MCP deployment with atlas-create-cluster available Atlas API credentials / service account for the project Customer approval of tier, region & charges
Configure the AI client with MongoDB MCP and an Atlas API credential/service account authorized for the target project.
Use atlas-list-orgs and atlas-list-projects to select the target project, and atlas-get-regions to resolve the region.
After the customer confirms tier, region, and billing, call atlas-create-cluster with the project, cluster name, M10 tier (or supported M10–M80), provider, region, and topology.
Poll with atlas-inspect-cluster until the status is IDLE.
Configure a least-privilege DB user and restricted network access, then retrieve and securely use the connection string.
💳 Billing
Charges accrue to the customer's Atlas organization from creation — confirm tier, region, and charges before running the tool. Confirm the desired tool exists in your MCP deployment before relying on it (see the MCP Server tool reference).
🖥️ Third option: Atlas UI
If your team is not yet onboarded as an approved Partner API design partner — or the customer simply wants direct control — the customer creates the paid cluster in the Atlas UI using the standard workflow, choosing M10 (or Flex for dev/test) at creation time. The Atlas picker shows the hourly price before they confirm, and billing goes to their own Atlas organization.

Which route should you recommend?

Match the route to the experience your customer is in.

Situation Recommended route
Customer wants a "Create MongoDB cluster" flow inside a partner product Partner API with delegated user authorization
Customer/operator wants natural-language Atlas administration from an MCP-connected AI client Remote MCP, if the required Atlas tools and credentials are configured
Partner does not have approved Partner API onboarding, or the customer wants direct control in Atlas Atlas UI using the standard create/upgrade workflow
🤝
In all cases: the customer owns the Atlas account and project, understands the paid-resource charges, approves the configuration before creation, and retains control over credentials and network access. M0 is where ideas start — paid tiers are where products run.

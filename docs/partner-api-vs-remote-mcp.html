MongoDB Atlas · Integration Paths

Integration paths for partners: Two ways to bring Atlas into partner platform.

🤝

Partner API

Partner API is the scripted integration path: after MongoDB onboards the partner and provisions OAuth credentials, a customer authorizes the app, which then calls Atlas Administration APIs directly to manage Atlas resources.

An approved partner application uses Atlas App Connections to obtain an Atlas user's authorization, then calls the Partner API directly with that user's permissions.

It is a way to connect and manage Atlas through the partner's product — it does not itself query documents inside a database.

🤖

Remote MCP

Remote MCP is the AI-driven path: when the customer's Atlas organization allows access, AI clients or agents use MongoDB-hosted tools in response to natural-language requests, to explore data or manage Atlas resources, within the organization's settings and user permissions.

MongoDB's hosted Model Context Protocol (MCP) server lets supported AI clients and agents use MongoDB tools.

Depending on permissions, an assistant can explore and query data or manage Atlas resources through those tools.

Two paths into Atlas

The Partner API path is a direct call from the partner's product. The Remote MCP path goes through MongoDB's hosted MCP server, which exposes MongoDB tools to AI clients.

How do they complement each other?

They overlap in some capabilities — but they are not direct substitutes. The right choice depends on the intended user journey, not solely on the operation being performed.

Partner APIDirect integration path for a partner application's product workflow
Remote MCPTool interface for an AI experience
Manage Atlas resourcesboth paths — when authorized

Overlap, not substitution. Both paths can be used to manage Atlas resources when authorized — but each exists for a different initiator and journey.

Access & examples

How each path is granted — and what a real journey looks like on each side.

🤝 Accessing the Partner API

Start with MongoDB's partner process. The public integration guide is intended for approved design partners — apply via the Become a Partner form with “Partner API” in the request.
User begins in the partner's application, signs in to Atlas, and authorizes that application.
The partner app calls permitted Partner API operations on the user's behalf.
Access is gated twice: by the user's Atlas role and by whether the Atlas organization allows third-party app connections.
💡 Example — app-building platform
A developer chooses MongoDB as the database for a new app. After the developer authorizes the platform, it can select or create an Atlas project and cluster in the developer's Atlas environment — subject to the developer's permissions. The platform handles the setup flow as part of its own product.

🤖 Accessing Remote MCP

Interactive — person + AI client Unattended — automated agent
Interactive use: a person connects a supported AI client from that client's marketplace and authorizes it in the browser.
Organization control: an Atlas Organization Owner controls whether AI clients can connect, and sets a read or read/write mode; the user's Atlas role further limits what the client can do.
Unattended agents: an administrator provisions an MCP configuration with assigned roles.
Both models use the hosted MongoDB MCP server.
💡 Example — AI-assisted data exploration
A developer connects a supported AI coding assistant to Atlas and asks what fields are in an orders collection. The assistant uses its permitted MongoDB tools to inspect the data and explain the result — the user remains within the AI client rather than a partner application's database-setup flow.
🔒
Neither route bypasses governance. Both paths are bound by the same permissions and organization controls that govern them — the user's Atlas role, org-level app-connection settings, and org-owner MCP modes.

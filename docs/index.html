Call Atlas on behalf of your users. No API keys required.

How the delegated flow works

Click through the four steps of the OAuth 2.1 Authorization Code + PKCE flow your app performs.

Redirect the user to Atlas. When a user clicks "Connect MongoDB Atlas" in your product, send them to the authorization endpoint with a PKCE challenge and CSRF state token.

HTTP — authorization request
GET https://cloud.mongodb.com/oauth/authorize
  ?response_type=code
  &client_id=
  &redirect_uri=https://app.example.com/oauth/atlas/callback
  &code_challenge=
  &code_challenge_method=S256
  &state=
  &resource=https://api.mongodb.com/api/atlas

The user logs in and grants consent. Atlas authenticates the user and shows a consent screen naming your application. Your app never sees the user's password.

User signs incloud.mongodb.com
→
Consent screengrants your app access
→
Redirect backwith authorization code

Exchange the code for tokens. Your backend POSTs the authorization code and PKCE verifier to the token endpoint — a back-channel call the browser never sees.

SHELL — token exchange
curl -X POST "https://authorize.mongodb.com/tokens" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -H "Authorization: Basic $(echo -n '<client_id>:<client_secret>' | base64)" \
  -d "grant_type=authorization_code" \
  -d "code=<authorization-code>" \
  -d "code_verifier=<pkce-verifier>" \
  -d "redirect_uri=https://app.example.com/oauth/atlas/callback"

Call the Atlas Admin API. Use the delegated access token as a Bearer token. It is scoped to what the logged-in user is allowed to do — no org-level API key needed.

SHELL — authenticated API call
curl "https://api.mongodb.com/api/atlas/v2/orgs" \
  -H "Authorization: Bearer <access_token>" \
  -H "Accept: application/vnd.atlas.2025-03-12+json"
